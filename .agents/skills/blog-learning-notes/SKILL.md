# 学习笔记与博客

目标是把用户的材料沉淀为 `src/content/posts/` 中可持续修改、便于复习和面试的中文 Markdown 文章。一次消息可能只是一篇文章的一小部分；以文章文件承载进度，后续消息继续整合。

## 定位文章

- 先查看用户提到的主题、书名、章节，以及 `src/content/posts/` 中相关旧文。主题相同且目标明确时续写原文；确实是独立主题时新建文章。目标有多种合理可能且会影响内容归属时，简短询问用户。
- 编辑现有文章时保留原有 frontmatter、日期、分类、标签、链接、图片和未涉及的内容；将新材料放进合适章节，消除重复，并修正因此产生的前后矛盾。不要每收到一段材料就另开一篇文章。
- 新文章参照最相近的现有文章：`YYYY-MM-DD-标题.md`，YAML frontmatter 包含 `title`、`description`、`author: zhang`、`date`、`categories`、`tags`、`pin: false`；仅在内容需要时加入 `math` 或 `mermaid`。日期用创建当日的本地时间，分类和标签沿用相关系列的惯例，不凭空创建书名或系列名。
- 分批提供材料是正常写作方式，新文章默认可在博客中查看（`draft: false` 或省略该字段）。只有用户明确要求隐藏文章或设为草稿时，才使用 `draft: true`。修改已有文章时不自行改变发布状态。

## 写作与校订

- 延续目标文章的标题层级、语气和细节密度。正文以概念、原理、适用条件、例子和容易混淆的边界组织。
- 将原文改写成清楚、准确的学习笔记，保留必要术语、代码、公式和关键限定条件。区分用户提供的原文、用户自己的结论和补充解释；不要把推断写成已核实事实，不要补造来源、版本、性能数据或实验结果。
- 遇到可疑或互相冲突的技术说法，核对官方文档或官方源码；确认与用户材料冲突时，直接按官方资料修正文章，并在回复中点明关键修正。无法核实的内容标明不确定性并向用户指出。保留来源链接或书籍章节信息（如果用户提供），适当标注引用出处。长段原文应提炼和转述，只有确需精确措辞时才短引。
- 优先让文章便于复习：解释“为什么”，展示最小可理解的例子，注明前提与例外；避免空泛扩写、重复结论以及未经请求的大规模重写。
- 以资深 Java 工程师的实际工作和面试准备为取舍标准，主动判断用户输入的知识深度。需要用于设计、编码、排障或解释关键原理的内容讲清楚；只需知道存在或能查文档的细枝末节，删除或用一句话概括。不要因为材料由用户提供，就默认全部保留；也不要仅因某知识属于数据库等相邻领域就删去对 Java 开发重要的部分。
- 在取舍用户材料后，主动检查是否缺少与本次主题高度相关、且资深 Java 工程师需要掌握并运用的关键知识。确有缺口时补入必要的概念、原理或实践边界，并核实新增的技术事实；不要借“发散”扩展到相邻的大主题，或补充仅需了解的细节。

## 多 agent 协作

每次新增或实质性修改文章时，由主 agent 定位目标文章、提供本次材料和相关旧文，并依次委派四个**独立的专门 agent**。主 agent 负责取舍、整合和最终交付；各 agent 返回审阅意见或拟写内容，由主 agent 统一编辑文件，避免并发覆盖。只审查本次新增内容及其影响到的上下文；已有文章不因此被无关重写。

1. **内容范围与事实审核 agent**：逐项判断用户输入的知识对资深 Java 工程师是“需要掌握并能运用”“了解即可”还是“可略去”，说明取舍理由；不能只做事实校对后把所有知识点原样保留。再检查本次主题是否缺少高度相关且必须掌握的知识，列出必要补充及其理由。逐项检查保留和拟补充内容的关键定义、公式、版本差异和例子。技术争议以官方文档、官方源码等一手资料核实，输出保留、概括、删减、补充及修正建议与证据链接，不臆造结论。
2. **内容优化 agent**：落实第一阶段的范围判断：完整讲解需要掌握的知识，了解即可的内容至多一句话带过，可略去的内容不写入正文或面试题；将确认必要的缺漏知识自然补入，再把材料组织成逻辑连贯的正文。适当补充直接相关的原理、适用前提、反例或实际排查方法，清楚区分已核实事实和解释性推断，不为充实篇幅而扩写。
3. **面试考点 agent**：从完成的正文提炼重点，拟写若干高相关的面试问题或场景案例及简明回答要点。优先覆盖“为什么、何时适用、如何排查、常见误区”；题数随材料多少调整，不声称有无法证实的真实出题概率。
4. **最终格式与内容审核 agent**：通读整合后的文章，检查事实是否仍与证据一致、正文与面试题是否互相矛盾，以及标题层级、代码块、列表、链接、术语和 frontmatter 是否符合现有博客。输出具体修改意见，主 agent 修正后再验证。

交接时，先把第 1 阶段结论交给第 2 阶段；主 agent 将第 2 阶段正文整合进文章后，把更新后的完整正文交给第 3 阶段；主 agent 合并面试题后，再把完整候选稿交给第 4 阶段。若终审发现事实问题，主 agent 修正后复核受影响的正文和面试题。

在文章末尾维护一个“面试考点与案例”章节；参考资料放在它之前。分批续写时更新、合并该章节的题目，删去重复题，并确保它始终是最后一个正文章节。材料尚少时只放少量有价值的题，后续随文章一起迭代。

若当前环境确实无法创建子 agent，主 agent 按四个职责完成工作，并在交付时说明未能执行多 agent 协作；不要声称已经由专门 agent 审过。

## 每次交付

- 修改文件后检查 Markdown/frontmatter 与相关链接；按变更范围运行 `npm run build` 或更轻的相关校验。不要仅为零碎笔记增量增加形式化测试。
- 回复中给出文章文件链接，简述这次新增或修正的知识点、仍待补充或核实之处，以及文章是否处于草稿状态。用户继续发送同一主题材料时，直接在此基础上工作。
- 简述本次对用户材料的范围取舍：哪些知识被完整保留，哪些被一句话概括或删去，主动补充了哪些关键知识，以及主要理由。不要把命令行输出、重复例子等呈现形式的精简冒充知识点删减。
