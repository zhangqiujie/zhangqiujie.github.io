# MySQL 连接（Join）原理深度解析

## 一、连接简介

### 1. 连接的本质
连接的本质是把各个连接表中的记录都取出来依次匹配组合，加入结果集并返回给用户。连接查询的结果集包含一个表中的每一条记录与另一个表中的每一条记录相互匹配的组合，这种结果集被称为**笛卡尔积**。如果表 t1 有 3 条记录，表 t2 有 3 条记录，连接后的笛卡尔积就有 $3 \times 3 = 9$ 行记录。在 MySQL 中，最基本的连接查询只需在 `FROM` 语句后跟多个表名，用逗号分隔即可。

### 2. 连接过程与过滤条件
若没有任何限制条件，多表连接产生的 Cartesian 积会非常巨大。因此，在连接查询中过滤特定记录组合极其必要。过滤条件主要分为两种：
* **涉及单表的条件**：只针对单个表的搜索条件（如 `t1.m1 > 1`）。
* **涉及两表的条件**：同时涉及两个表的过滤条件（如 `t1.m1 = t2.m2`），用来进行表与表之间的记录匹配。

以查询语句 `SELECT * FROM t1, t2 WHERE t1.m1 > 1 AND t1.m1 = t2.m2 AND t2.n2 < 'd';` 为例，其大致执行过程如下：
1.  **确定驱动表**：首先选取代价最小的单表访问方法（const、ref、range、all 等）执行驱动表的单表查询。假设 t1 为驱动表，通过全表扫描（all）找出满足 `t1.m1 > 1` 的记录。
2.  **查询被驱动表**：针对驱动表产生的结果集中的每一条记录，分别到被驱动表（t2）中查找匹配的记录。此时涉及两表的条件会转化为被驱动表的单表常数条件。如果驱动表查出 2 条记录，被驱动表就需要被查询 2 次。
> **核心结论**：在两表连接查询中，驱动表只需要访问一次，而被驱动表可能被访问多次。访问次数取决于驱动表符合单表过滤条件的结果集记录数。

## 二、内连接与外连接

在实际业务中，由于数据不全（如某些学生缺考，成绩表无记录），单纯的连接会过滤掉这些信息。为了解决“驱动表中的记录即使在被驱动表中没有匹配记录，也需要加入结果集”的问题，引入了外连接。

### 1. 基本概念
* **内连接（INNER JOIN）**：若驱动表中的记录在被驱动表中找不到匹配的记录，该记录不会加入到最后的结果集。对于内连接来说，驱动表和被驱动表是可以互换的，不影响最终结果。
* **外连接（OUTER JOIN）**：即使驱动表中的记录在被驱动表中没有匹配的记录，也仍然需要加入到结果集，此时被驱动表对应的字段使用 `NULL` 值填充。外连接的驱动表与被驱动表关系固定，不能随意互换。
    * **左（外）连接**：选取左侧的表为驱动表。
    * **右（外）连接**：选取右侧的表为驱动表。

### 2. WHERE 与 ON 子句的语义区别
* **WHERE 子句**：不论是内连接还是外连接，凡是不符合 `WHERE` 子句中过滤条件的记录，都绝对不会被加入最后的结果集。
* **ON 子句**：专门为外连接中“被驱动表匹配失败时是否保留驱动表记录”的场景提出。如果无法在被驱动表中找到匹配 `ON` 子句条件的记录，驱动表记录仍会加入结果集，被驱动表字段填 `NULL`。
> **注意**：在内连接中，`ON` 子句和 `WHERE` 子句是完全等价的。最佳实践通常是将单表过滤条件放在 `WHERE` 中，将两表连接条件放在 `ON` 中。

### 3. 语法形式
* **左外连接**：`SELECT * FROM t1 LEFT [OUTER] JOIN t2 ON 连接条件 [WHERE 普通过滤条件];`
* **右外连接**：`SELECT * FROM t1 RIGHT [OUTER] JOIN t2 ON 连接条件 [WHERE 普通过滤条件];`
* **内连接等价写法**：以下写法在 MySQL 中完全等价，推荐使用语义最明确的 `INNER JOIN`。
    ```sql
    SELECT * FROM t1, t2;
    SELECT * FROM t1 JOIN t2;
    SELECT * FROM t1 INNER JOIN t2;
    SELECT * FROM t1 CROSS JOIN t2;
    ```

## 三、连接的底层原理与算法

### 1. 嵌套循环连接（Nested-Loop Join）
这是最简单、最基础的连接算法。其过程如同一层嵌套的 `for` 循环：驱动表只访问一次，遍历驱动表的结果集，针对每一条记录，都去被驱动表中进行单表查询。
```python
for each row in t1: # 遍历驱动表结果集
    for each row in t2: # 遍历被驱动表，寻找匹配记录
        if row satisfies join conditions:
            send to client
```
这种算法的致命缺点是，若驱动表结果集有 $N$ 条记录，被驱动表就必须被完整扫描 $N$ 次。若被驱动表数据量极大且无索引，会导致大量的磁盘 I/O。

### 2. 使用索引加快连接速度
为了避免对被驱动表进行高代价的全表扫描，可以利用索引优化被驱动表的查询：
* **eq_ref 访问方法**：如果被驱动表的连接列是主键或唯一二级索引列，那么在连接查询中对其进行等值查找的代价是常数级别的，这是效率极高的连接方式。
* **ref/range/index 访问方法**：在被驱动表的连接列或普通单表过滤列上建立二级索引。只要 `二级索引 + 回表` 的代价小于全表扫描，MySQL 就会采用索引来大幅度提升被驱动表的查询速度。


### 3. Hash Join（哈希连接）
MySQL 8.0.18 引入了 Hash Join，用来替代过去在“大表且无索引”场景下表现极差的块嵌套循环连接（BNL），在特定场景下其运行速度甚至能超越传统的索引连接。

#### 工作原理

Hash Join 的核心思想是利用内存中的**哈希表**来消除嵌套循环。它主要分为两个阶段：
* **构建阶段（Build Phase）**：MySQL 优化器会自动选择两个表中数据量较小（按字节大小计算）的表作为构建表（Build Table）。遍历该表的所有记录，以连接列（Join Key）作为哈希键，通过哈希函数计算出哈希值，并将整行数据存入内存中的哈希表中。
* **探测阶段（Probe Phase）**：扫描另一个较大的表，称为探测表（Probe Table）。对于探测表中的每一条记录，同样对其连接列计算哈希值，然后直接去内存的哈希表中进行等值查找。如果哈希桶中存在匹配的记录，则将两表数据合并输出，存入结果集。

#### 内存不足时的“分片”降级策略（磁盘溢出）
Hash Join 的执行内存大小受系统变量 `join_buffer_size` 控制。如果构建表太大，内存装不下，MySQL 会启动特殊降级策略（Hybrid/Grace Hash Join）。它会利用同一个哈希函数，把构建表和探测表的数据通过计算，同时切分成多个互不相交的小片（Chunk 文件）溢写到磁盘。接着，MySQL 会在内存中以“分片”为单位，逐个进行构建和探测。这虽然引入了磁盘 I/O，但依然远比嵌套循环高效。

#### 触发场景与使用限制
* **自动触发的条件**：两个表进行连接查询，连接列上**没有可用的索引**，且连接条件必须是**等值连接**（例如 `t1.c1 = t2.c1`）。从 8.0.20 版本开始，非等值条件（如 `>` 或 `<`）也可以在 Hash Join 后作为附加过滤条件（Filter）使用。使用 `EXPLAIN FORMAT=TREE` 关键字可以查看到 `Inner hash join` 的执行计划。
* **控制命令**：在 MySQL 8.0.20+ 中，Hash Join 彻底取代了旧的 BNL。你可以通过控制块嵌套循环的开关或 Hint 来间接控制它。
    ```sql
    SET optimizer_switch = 'block_nested_loop=off'; -- 全局控制开关
    SELECT /*+ NO_BNL(t1, t2) */ * FROM t1 JOIN t2 ON t1.id = t2.id; -- 通过 Hint 禁用
    ```
* **核心局限性**：Hash Join **不会使用索引**。如果在连接列上建立了合适的索引，MySQL 依然会优先选择代价更低的索引嵌套循环连接（Index Nested-Loop Join）。因此，Hash Join 是作为“缺乏索引时的保底王牌”，而不是鼓励不建索引。
