## 索引的代价

- 空间的代价：每创建一个索引都要创建B+树占用更多空间。

- 时间的代价：每次对数据库的增删改，都需要对聚簇索引或者二级索引的节点修改，或者维护节点顺序。需要消耗额外的时间。

## B+树索引的适用条件

创建索引 (name, birthday, phone_number)

那么Mysql会为这个索引创建出一棵B+树, 并且树内每个记录按照 name, birthday, phone_number 的值依次排序。

### 全值匹配

如果我们的搜索条件中的列和索引列一致的话，这种情况就称为全值匹配（where 的顺序不重要）。

```
SELECT * FROM person_info WHERE name = 'Ashburn' AND birthday = '1990-09-27' AND phone_number = '15123983239';
```

这个联合索引是按 name → birthday → phone_number 依次排序的，所以查询时会先用 name 快速定位到一段范围，再在这段范围内用 birthday 继续缩小范围，最后如果前两列都相同，再用 phone_number 精确定位到具体记录。

本质就是：逐层缩小范围，一层一层往下“筛”。


### 匹配左边的列

where 包含了左边的列。

```
SELECT * FROM person_info WHERE name = 'Ashburn' AND birthday = '1990-09-27';
```

只要查询条件中包含联合索引最左边的列，后续列即使不出现，也仍然能利用索引的有序性来快速定位 name 对应的数据范围，再通过 birthday 缩小数据范围。

如果是：

```
SELECT * FROM person_info WHERE birthday = '1990-09-27';
```

因为 B+ 树是先按 name 排序的，birthday 只有在 name 相同的前提下才有序；现在跳过 name 直接按 birthday 查，相当于在一个“按 name 分块排好序”的结构里乱找 birthday，没有连续有序性可利用，只能全表扫描。

### 匹配列前缀

所以一个排好序的字符串列其实有这样的特点：
- 先按照字符串的第一个字符进行排序。
- 如果第一个字符相同再按照第二个字符进行排序。
- 如果第二个字符相同再按照第三个字符进行排序，依此类推。

所以如果sql里给定的某个字符串前缀，依然可以通过索引，缩小数据范围。

```
SELECT * FROM person_info WHERE name LIKE 'As%';
```

### 匹配范围值

```
SELECT * FROM person_info WHERE name > 'Asa' AND name < 'Barlow';
```

这样会先利用索引找到第一条name大于Asa的二级索引记录，判断是否name < 'Barlow'，如果符合就回表返回完整记录，继续往下找，不符合就结束查找。

**范围匹配会使下一个索引列失效**

比如：
```
SELECT * FROM person_info WHERE name > 'Asa' AND name < 'Barlow' AND birthday > '1980-01-01';
```

在name使用完索引找到数据范围后，因为找到的name可能不一样，birthday在这些数据内就不是有序的，无法快速缩小范围。

但是如果换成name是精确匹配，birthday是范围匹配，两者都会用上索引。

### 用于分组和排序

ORDER BY 如果刚好匹配索引的排序规则（比如 name, birthday, phone_number），MySQL 可以直接利用 B+ 树的有序性，按索引顺序读取数据，避免内存或磁盘排序（filesort），效率更高。

但索引排序有几个限制：

1. 必须按索引列的顺序使用（可以用左边连续前缀），否则无法利用索引
2. 排序方向必须一致（要么全 ASC，要么全 DESC），混用会失效
3. 如果排序列不在同一个索引中，也无法使用索引排序
4. 如果对列做函数或表达式（如 UPPER(name)），索引也失效

GROUP BY 本质和 ORDER BY 类似，也是按列分组排序。如果分组列的顺序与索引一致，也可以直接利用 B+ 树的有序性完成分组，从而避免额外的内存分组开销。

## 回表的代价

```
SELECT * FROM person_info 
WHERE name > 'Asa' AND name < 'Barlow';
```

这个执行过程分两步：

1）先走二级索引（idx_name_birthday_phone_number）
在 B+ 树中找到 name 在范围内的记录，这一步只拿到索引列 + 主键 id。

2）再回表
因为是查询所有列，还需要 country 字段，所以必须用每条记录的 id 去聚簇索引再查一次完整行，这个过程就是回表。

**为什么回表慢**
- 二级索引里数据是按 name 有序的 → 读取是顺序 I/O（快）
- 回表要按 id 去聚簇索引查 → id 是乱的 → 随机 I/O（慢）

所以回表次数越多，性能越差，极端情况下（比如 90% 都要回表），还不如直接全表扫描。

**优化器怎么选**

MySQL 会根据“需要回表的行数”来决定：

回表少 → 用「二级索引 + 回表」
回表多 → 直接「全表扫描」

如果加了`limit`少数, 只需要很少回表数据，优化器更容易选择走索引。

### 覆盖索引

当查询列都是索引列时，可以在二级索引时完成完整查询数据的获取，减少回表带来的性能损耗。
