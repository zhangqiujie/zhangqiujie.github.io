优化器选择执行计划时，会估算不同访问方案的成本。这里的“成本”是用于比较方案的相对数值，不等于实际执行时间。读取页面、检查记录是否满足条件等操作都有各自的**成本常数**。

## 单表查询的成本

对于一条单表查询，优化器会考虑全表扫描和可用的索引访问方案，估算各自的成本，再选择它认为成本较低的执行计划。可以先从“有哪些候选索引”和“全表扫描要花多少成本”两步理解。

### 1. 找出可能使用的索引

如果搜索条件能够利用索引列确定查找范围，该索引就可能成为候选索引。例如索引列与常量进行等值、大小比较、`IN`、`BETWEEN` 或前缀 `LIKE` 匹配时，优化器可能据此构造索引范围。`IS NULL` 等条件也可能使用索引。

这些候选索引可以在 `EXPLAIN` 的 `possible_keys` 列中查看；最终选用的索引看 `key` 列。**出现在 `possible_keys` 中，不代表一定会使用该索引。** `NOT IN`、`!=`、`IS NOT NULL` 等条件是否适合索引访问，还要结合索引结构、数据分布和成本判断，不能只凭运算符断定。

### 2. 估算全表扫描的成本

全表扫描需要读取聚簇索引的数据页，并逐条检查记录是否满足搜索条件。因此，可以把成本粗略分成两部分：

- **I/O 成本**：读取数据页的成本。
- **CPU 成本**：处理记录、判断搜索条件的成本。

用下面的命令可以查看表的统计信息：

```sql
SHOW TABLE STATUS LIKE '表名';
```

其中，`Rows` 是 InnoDB 表的估算行数；`Data_length` 是为聚簇索引分配的近似空间。用 `Data_length / innodb_page_size` 可以粗略换算聚簇索引已分配的页数，但这不等于本次扫描实际发生的物理读页数；页面可能已经在缓冲池中，已分配页也不都等同于有效数据叶子页。`innodb_page_size` 的默认值为 16 KiB。

以 MySQL 8.0 的默认成本常数为例，可以用下面的教学模型理解主要成本量纲：

```text
磁盘块读取成本 ≈ 聚簇索引已分配页数 × 1.0
记录条件检查成本 ≈ 估算行数 × 0.1
```

`1.0` 对应默认的 `io_block_read_cost`，`0.1` 对应默认的 `row_evaluate_cost`；内存块读取另有默认值为 `0.25` 的 `memory_block_read_cost`。这些常数是优化器比较候选计划时使用的相对权重，不是毫秒。

上式只用于帮助理解 I/O 与 CPU 成本的来源，不是 MySQL 表扫描成本的源码公式，也不能用来精确复算 `EXPLAIN FORMAT=TREE` 展示的 `cost`。实际估价还会考虑页面是否可能驻留内存、访问方法及其他操作成本。

**注意**：成本常数可以调整，`Rows` 和 `Data_length` 也都是估算值。不要把手算结果当作执行计划成本或实际耗时的精确值。

### 3. 估算使用不同索引的成本

存在可用索引时，优化器会估算各个可行访问方案的成本，并与全表扫描比较。候选方案既可能使用某一个索引，也可能在条件允许时使用**索引合并**（`Index Merge`），对同一张表的多个索引范围扫描结果做交集、并集或排序后并集（`intersection`、`union`、`sort-union`）。这些算法名称了解即可，重点仍是优化器会比较候选方案的总成本。

对于需要“扫描二级索引，再根据主键回表”的方案，可以抓住两个影响成本的量：

1. **索引范围的数量及扫描量**：范围越多，通常需要更多次定位；每个范围内还可能扫描不同数量的索引记录。不能认为一个范围无论多大都只需读取一个索引页。
2. **预计回表的记录数**：需要完整行的查询可能按二级索引记录中的主键值访问聚簇索引。预计命中的记录越多，回表成本通常越高。覆盖索引不需要回表；索引条件下推（ICP）会先在二级索引条目上判断可下推条件，从而减少读取完整行的次数，但不会减少索引范围本身需要扫描的条目数。

优化器需要先估计范围内有多少记录。对于某些等值范围，它可以在范围两端进行**索引探测**（index dive）来估计行数；在一些情况下也会改用索引统计信息。这个行数是估计值，不是先完整扫描范围再精确计数。

#### 等值范围很多时：使用索引统计信息

`IN` 在非唯一索引列上可能形成多个单点范围。逐个范围做 index dive 有助于估计命中行数，但范围很多时，优化阶段本身也会变慢。`eq_range_index_dive_limit` 控制何时改用索引统计信息：在 MySQL 8.0 中默认值为 `200`，等值范围数量达到该值时改用统计信息；设为 `0` 则始终使用 index dive。这里比较的是**等值范围数**，不应简单等同于 SQL 中写了多少个参数。

统计信息可通过 `SHOW TABLE STATUS` 的 `Rows` 和 `SHOW INDEX FROM 表名` 的 `Cardinality` 查看。后者是索引中不同键值数量的**估计值**。对于单列索引，可用 `Rows / Cardinality` 粗略理解平均每个值对应多少行；例如估算有约 10,000 行、约 1,000 个不同值，平均每个值约对应 10 行。这只是平均值：数据倾斜时，某个具体值的命中行数可能与它相差很大，`IN` 中多个值的命中行数也不能机械地相乘。

**实践要点**：遇到很长的 `IN` 列表或优化器选错索引时，除了检查执行阶段，也要关注优化阶段的开销与统计信息是否过时；结合 `EXPLAIN` 查看行数估计，必要时用 `ANALYZE TABLE` 更新统计信息，再比较计划。不要仅凭 `Cardinality` 推断某个查询一定会走索引。

从组成上看，非覆盖的二级索引访问成本可以理解为：

```text
总成本 ≈ 二级索引定位与扫描成本 + 回表读取成本 + 记录条件检查成本
```

不能把“每个范围固定读取一页、每次回表固定读取一页”当作 MySQL 8.0 的通用成本公式；索引扫描、回表、缓存命中和条件检查的估价还取决于所选访问方式及成本模型。

## 连接查询的成本

### 扇出决定后续访问量

在**嵌套循环连接**中，可以用下面的简化关系理解两表连接的成本：

```text
连接成本 ≈ 访问前一张表的成本
         + 传给下一张表的行数 × 单次访问下一张表的成本
```

这里可以把传给下一张表的估计行数理解为当前连接前缀的**扇出**（fanout）。它越大，后续表可能被访问的次数越多。因此，优化连接查询既要关注前面表过滤后还剩多少行，也要关注后面表能否通过连接列高效查找。

### Condition filtering：估算过滤后的行数

索引范围可能先找出一批候选行，但其他 `WHERE` 条件还会进一步过滤。优化器会估计这些额外条件的过滤比例，用来预测传给下一张表的行数。在传统格式的 `EXPLAIN` 中，可以用下面的关系粗略理解这一估计：

```text
传给下一张表的估计行数 ≈ rows × filtered / 100
```

`rows` 是预计检查的行数，`filtered` 是预计通过表条件的百分比。`filtered` 关注尚未被当前访问方法计入、但会在把行传给下一张表前应用的额外条件。例如，索引范围预计取出 100 行，其他条件预计保留 20%，则下一张表接收的估计输入约为 20 行。

这仍是统计估算。数据倾斜、统计信息陈旧或条件之间存在相关性时，估计值可能明显偏离实际。MySQL 8.0.18 起可以使用 `EXPLAIN ANALYZE` 对比各迭代器的估算行数、实际行数、耗时和循环次数，定位偏差从哪一步开始。它会真正执行语句，因此分析线上高开销语句时必须谨慎。

上述公式用于理解嵌套循环。MySQL 8.0.18 起还支持 Hash Join；8.0.20 起 Block Nested-Loop 被移除，Hash Join 的适用范围也扩展到非等值连接、外连接等场景，因此不能用嵌套循环公式解释所有连接计划。

### 连接顺序与访问方法一起看

内连接通常允许优化器调整表的访问顺序。不同顺序会改变前面连接前缀的扇出，以及后续表可用的访问方法：连接列有合适索引时，后续表可能使用 `ref` 或 `eq_ref`；否则还要比较 Hash Join 等方案。外连接的顺序受语义约束；如果 `WHERE` 条件会拒绝内表补出的 `NULL` 行，即形成 null-rejected 条件，优化器可能把外连接简化为内连接，再重新考虑连接顺序。

多表连接的潜在顺序会随表数快速增加。优化器会结合成本估计与剪枝控制搜索范围；`optimizer_search_depth`、`optimizer_prune_level` 是相关配置，但日常排查应先看执行计划和行数估计，不应把调参当作首选修复方式。

**实践要点**：先找出哪一步的预计输出行数或实际循环次数突然变大，再检查过滤条件、连接列索引和统计信息。减少无效输入、降低后续表访问成本，通常比只盯着 SQL 里表的书写顺序更有帮助。

## 面试考点与案例

### 1. 查询条件有索引，为什么优化器仍可能选择全表扫描？

索引存在只说明它是候选访问路径，不代表使用它的总成本最低。非覆盖二级索引命中大量记录时，需要先扫描索引再按主键回表，随机访问和条件检查的成本可能超过扫描聚簇索引。统计信息陈旧、数据倾斜或选择率估算错误，也可能让优化器误判成本。排查时应先查看 `possible_keys`、`key`、`rows` 和 `filtered`，再在安全环境中用 `EXPLAIN ANALYZE` 对比实际行数，而不是直接强制索引。

### 2. `rows` 和 `filtered` 如何影响连接顺序？

在传统格式的 `EXPLAIN` 中，可以用 `rows × filtered / 100` 粗略估算当前表传给下一张表的行数。这个值越大，嵌套循环中后续表被访问的次数通常越多，因此优化器会同时比较不同连接顺序产生的扇出，以及后续表能否使用 `ref`、`eq_ref` 等低成本访问方法。两列都是估算值，不能只看其中一个。

### 3. 很长的 `IN` 列表为什么可能改变行数估计和执行计划？

非唯一索引上的 `IN` 可能形成多个等值范围。范围较少时，优化器可以逐个执行 index dive；范围很多时，为控制优化阶段开销，可能改用索引统计信息估算。MySQL 8.0 中 `eq_range_index_dive_limit` 默认值为 `200`，等值范围数达到该值时改用统计信息，设为 `0` 表示始终执行 index dive。统计信息只反映总体分布，数据倾斜时可能导致命中行数估算失真，进而改变索引选择。

### 4. 如何用 `EXPLAIN ANALYZE` 定位成本估算失准？

MySQL 8.0.18 起，可以比较每个迭代器的估算行数与实际行数，并结合耗时和 `loops` 找到偏差首次明显扩大的节点。如果估算行数远小于实际行数，应检查统计信息是否陈旧、数据是否倾斜、过滤条件是否相关；如果循环次数异常增大，则继续检查连接顺序和连接列索引。`EXPLAIN ANALYZE` 会真实执行语句，在线上分析高开销查询时必须谨慎。

### 5. 覆盖索引和索引条件下推分别减少了什么成本？

覆盖索引包含查询所需的全部列，可以直接从二级索引返回结果，省去回表读取完整行的成本。索引条件下推（ICP）是在扫描既定索引范围时，先用索引条目中的列判断可下推条件，减少不必要的完整行读取；它不会缩小访问方法已经确定的索引扫描范围。两者都可能降低回表相关成本，但机制不同。
